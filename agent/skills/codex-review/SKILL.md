# 叫 Codex 當審核副手

這個技能要的是**第二雙眼睛**：我自己做的東西，我自己看不出問題（劇情邏輯、假通過、不該公開的內容）。所以流程是「我做 → Codex 審 → 我改 → Codex 複審到沒有擋點 → 才回報使用者」，不是做完順手問一句。

作者實測：一次專案整理送審十五輪，每一輪都抓到真問題——三支必跑檢查工具遇到壞檔會當成通過、準備公開的工具檔頭寫了片名和別人的原話、覆蓋率分母漏算。

## 怎麼送

用 `tools/codex_review.cmd`（說明在 `tools/codex_review.py` 檔頭）。**不要手寫 `codex exec` 指令**：唯讀沙盒讀不到本機檔，材料全部要從 stdin 餵，手寫時最常出的三個錯這支工具都擋掉了——用 `cut -c` 截行把中文切壞（Codex 整份拒收）、忘了指定思考強度（設定檔預設是 xhigh）、下一輪沒附上一輪的意見。

```
tools\codex_review.cmd --ask ask.md --attach 檔1 檔2 … [--image 圖 …] --name <主題> --outdir <資料夾>
tools\codex_review.cmd --ask ask2.md --attach … --with-prev --name <同一個主題> --outdir <同一個資料夾>     # 第二輪起
```

- `--ask`：我要問的話，寫成一個 UTF-8 文字檔（用 Write 工具寫，不要用 bash heredoc：反斜線會被吃掉，Windows 路徑會變成亂碼）。
- `--attach`：要它看的東西，**整份原文**附上。指令輸出（`git diff`、測試結果）先存檔再附。
- `--image`：畫面類的一定要附圖（每秒一格總表、封面、網頁截圖）；沒有圖它只能審文字。
- `--outdir`：片子放 `<片>/review/codex/`；專案整理、工具放暫存區。提示詞、意見、紀錄都會留檔，之後查得到。
- 一輪（high）通常 3–6 分鐘，用背景執行，等的時候做別的事。
- 模型不被接受時：看 `~/.codex/models_cache.json` 有沒有 `gpt-6.2-astra`，沒有就 `npm i -g @openai/codex` 更新（要 0.170.0 以上）。

送出去的內容會到 OpenAI：不附金鑰、個資，只附這次判斷需要的檔。

## 提問檔怎麼寫

各種情況的範本在 [references/prompt-templates.md](references/prompt-templates.md)（計畫、程式與工具、劇本、成片、公開推送）。共同的寫法：

1. **先給事實，再給我的做法。** 它看不到專案，判斷全靠我給的東西。計畫類要附專案入口檔（`CLAUDE.md`）全文；程式類要附全文或完整 diff，加上我實際跑過的測試與結果。
2. **要它獨立審，不是確認。** 開頭寫明「請獨立審核，不要只是確認」；換新模型或已經審過幾輪時，加「不要只確認前幾輪」。
3. **問題編號、限字數、要結論。** 例：「1. 有沒有錯或漏？2. 最大的三個風險，各附改法。3. 可不可以開工？直接講結論，700 字以內。」沒有限字數它會寫很長，重點被稀釋。
4. **照實寫，包括不利的事。** 沒跑的測試不要寫成跑了；數字要是真的數出來的（我寫過「48 項全過」，實際是 45 項，被迫在下一輪更正）；沒照它意見做的地方直接講，附理由。
5. **第二輪起請它分擋點與建議，擋點照審核對象定義。** 審到後面它會一直找得到更邊角的情況，所以請它分成「(A) 擋」和「(B) 不擋的改善建議」。什麼算擋，要照這次審的東西寫，寫窄了真正的問題會被歸到 (B) 放過去：
   - **劇本、成片**：劇情邏輯對不上（人數、年級、時間、誰是誰、規則來源、伏筆沒兌現）、第一次看的觀眾看不懂、畫面連戲錯誤、使用者叫修過的同類問題再犯。
   - **程式、工具**：在實際用途下會把有問題的東西報成通過、會弄壞資料或別人的檔。寫明實際用途（例：本機 H3 生成的固定 24fps、3–12 秒片段）。
   - **公開推送**：會洩漏不該公開的內容、程式錯誤。
   - **計畫、專案結構**：會弄壞現有流程、遺失規則、害到其他工作階段。
   這不是叫它放水，是讓它把力氣放在真的會出事的地方。

## 意見回來之後

- **逐點判斷，不是照單全收，也不是找理由不做。** 大部分意見是對的，照做並補測試。不採用時要有它不知道的事實當理由，寫進下一輪讓它反駁。兩個實例：它建議每個新任務開獨立 worktree，但做片的素材不在版控、worktree 裡拍不了片 → 改成「每片單一寫入者、只提交指名路徑」，它同意；它要求整集掃描時缺檔一律回錯誤，但真實片資料夾每支都有幾個生成失敗留下的空資料夾 → 改成「列出來請人確認」，附了五支片的統計，它同意。
- **它是讀程式推論，沒有執行。** 它說有問題的地方，自己重現一次再修；它說沒問題的地方，不代表測過。我自己的測試不能省。
- **修完要重測、重送。** 它指出一個假通過，通常同一類還有別的；修的時候把同類的一起找。
- **片子以劇情品質優先**：它指出劇情有問題，該重寫就重寫、該重拍就重拍，不為了省時間保留有問題的鏡頭。
- **工具回傳 0 只代表拿到意見**，不代表通過；要讀它的結論。
- **什麼時候算審完**：它明說「沒有大問題／可以開工／可以推送」，或只剩 (B) 類建議。還有 (A) 類就繼續改，不要帶著擋點回報使用者。
- **回報使用者時**：講它抓到什麼、我怎麼處理、哪些沒採用與原因。不要只說「Codex 審過了」。

## 各種情況要附什麼

| 審什麼 | 一定要附 | 重點問 |
|:---|:---|:---|
| 計畫、專案結構 | 盤點到的事實、我的提案、`CLAUDE.md` 全文 | 會不會弄壞流程、遺失規則、害到其他工作階段；優先順序；漏了什麼 |
| 程式、共用工具 | 全文或完整 diff、實測指令與結果 | 假通過（壞檔、缺檔、空輸入、門檻是 nan）、放行邏輯的洞、驗證缺哪個案例 |
| 劇本 | 本集劇本、前幾集的台詞字卡、系列設定、使用者歷次意見 | 跨集邏輯（人數、年級、時間、誰是誰、規則從哪來）、伏筆有沒有兌現、第一次看的人懂不懂、笑點與記憶點 |
| 成片 | 本集與前幾集照剪接順序的台詞字卡、每秒一格總表（`--image`）、劇本、前幾集的參考畫面、使用者歷次意見 | 上面那些（含笑點／記憶點／爽點），加上畫面連戲 |
| 公開推送 | 完整 diff、新增檔全文、掃描結果、跟遠端的同步狀態 | 不該公開的內容（個資、本機路徑、金鑰、片名鏡號時間碼、任何人的原話）、程式錯誤 |
| 網頁、遊戲 | 整套截圖（`--image`）、原始碼 | 第一次用的人卡在哪、文字與版面、手機版 |

公開版的去識別化慣例（Codex 會照這個擋）：「使用者」改寫成「作者」或技術現象；不放片名、版本、時間碼、鏡號；不引用任何人的原話；專案路徑改成通用路徑。既有公開檔案有同樣寫法，不代表新檔可以這樣寫。

## 相關
